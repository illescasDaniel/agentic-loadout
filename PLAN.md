# Plan: model tiers for delegated work

Status: proposal for review, 2026-11-03 (human decisions applied, see Review notes). No implementation is authorized by this plan alone.

## Goal and decisions

Make small-model delegation available for well-defined work while preserving language-specific navigation and independent review. Keep the current standard coders; add generic and language-specific `-small` counterparts. The small variants and the reviewer are not opt-in: they are installed alongside the standard coders. The orchestrator chooses an appropriate role for the task and honors the developer's choice.

When a developer mentions usage limits or asks for multiple parallel subagents, suggest small-model agents as an option when appropriate. Explain the tradeoff briefly and proceed according to their answer. An explicit request to use a tier is sufficient; do not ask again. Do not automatically switch models merely because limits are mentioned, read usage data, configure a status line, or infer that quotas are separate. Routine delegation without either trigger should not generate repeated suggestions. Keep established preferences for the session and avoid prompting on every block.

The earlier project implementation plan is preserved in `docs/original-implementation-plan.md` (currently untracked: commit it, otherwise it only exists in the working tree). `README.md` (line 124), `src/agentic_loadout/instructions.py` (docstring), `install.py` and `tests/conftest.py` still cite the old `PLAN.md` / `PLAN.md §8a`; WP0 repoints them.

## Current behavior and constraints

- `assets/agents/coder.md` is a Sonnet agent. `coders.py` builds each language coder from that shared body plus its navigation fragment and tool list. The language routing sections currently direct all relevant code to the standard specialist.
- `assets/development-workflow.md` describes the generic and language coders, independent SDD grading, task routing and orchestrator responsibilities. The `code-grader` is sourced from the installed SDD skill and is an Opus final grade, not a general implementation reviewer.
- `vendors.py` converts Claude-format agents for Cursor and Codex. Cursor currently inherits the parent model; Codex conversion currently drops the Claude model. Merely naming an agent `small` therefore does not guarantee a smaller model.
- Code facts the implementation must respect (verified against the tree):
  - `agents.install_agents` installs every `assets/agents/*.md` (non-recursive glob, skipping `*.head.md`). The small-coder supplement and `code-reviewer.md` must not be installed by that glob accident (the supplement is not an agent, and the glob knows nothing about coder selection). Keep them in a separate directory, `assets/agents/tiers/` (not matched by the glob), and install them through explicit code that runs exactly when coder agents are installed. Check the wheel still ships the directory (CI builds the wheel and runs the CLI from an empty venv).
  - `write_bytes` never overwrites a differing file without `--force` (it logs `skipped`). Consequences: (a) any change that alters the bytes of an existing standard agent or of `.agents/development-workflow.md` is invisible to existing users until `--force`, so tier guidance must not live in `development-workflow.md`; marker sections in `AGENTS.md` are the only content replaced in place; (b) existing standard agent files must stay byte-identical, and a re-run must add the new files without touching customized ones.
  - `vendors.convert_agent` hardcodes `model: inherit` for Cursor and never writes `model` for Codex; Codex `model_reasoning_effort` comes only from the source `effort` field. `agent_source` is currently unused; do not rely on it for round trips.
  - `coders.agent_bytes` drops `name`, `description` and `disallowedTools` from `coder.md` and keeps the rest (`model`, `color`); small variants need `model`/`effort`/`color` overrides there. `vendors._is_read_only` keys off `Edit` in `disallowedTools`: the reviewer must list `Edit` or Cursor `readonly` and the Codex read-only prefix are not emitted.
  - `coders.status()`/`list_coders()` only look at the standard agent; `Coder.section` is one marker section named after the agent (`coder-python`). Rendering small-tier routing inside that same section keeps re-runs replacing in place.
  - `templates/agents-rules.md` hardcodes `architect`, `coder`, `code-grader`, `utility`. The standalone `coders` flow (`install._run_coders`) writes no workflow file and no `agents` section, so anything it installs must be self-explanatory from its own routing section.
  - There is no uninstall and `_run_install` states "Nothing is rolled back"; re-runs are the recovery path.
- Coders may be installed without the generic agent suite through `agentic-loadout coders`. `--without agents`, `--without sdd` and `--without agemem` are independent choices. Navigation MCPs and generated instruction sections must still work in those combinations.
- Existing user-owned instructions, agent files and MCP entries must retain the installer's current conflict and `--force` behavior. The installer is project-scoped; keep the established personal-settings and exclusion semantics.

## Roles and model policy

| Role | Agent names | Claude default | Codex default | Responsibility |
|---|---|---|---|---|
| Small implementation | `coder-small`, `coder-python-small`, `coder-typescript-small`, `coder-swift-small` | Haiku, high effort where supported | Luna, high effort where supported | Execute bounded briefs, use the language MCP and report uncertainty. |
| Standard implementation | Existing `coder` and `coder-<language>` | Sonnet | Terra | Handle normal implementation and more ambiguous or intricate work. |
| Independent reviewer | `code-reviewer` | Sonnet | Terra | Review the actual changes and evidence; return actionable findings. |
| Architecture/advice | Existing `architect` | Opus | Sol by default; Astra available for especially demanding work | Resolve architecture and difficult decisions; do not make model choice a claim of equivalence. |
| Utility | Existing `utility` | Haiku | Luna | Bounded checks and mechanical tasks, subject to existing permissions and workflow. |
| Final SDD grade | Existing `code-grader` | Opus | Sol or Astra, subject to client support | Preserve the existing SDD skill's independent final grade and protocol. |

The Codex model names (Luna, Terra, Sol, Astra) are authoritative: they come from Codex itself, so they go straight into the `CLIENT_MODELS` table. WP1 still records the exact accepted ID spelling and the client's behavior for an unknown ID. Only if the spike shows a name is rejected does that role fall back to no explicit Codex model (inherit the session), with that disclosed. `code-reviewer` is a new, read-only agent (`disallowedTools: Edit, Write, NotebookEdit` plus the agemem write tools, as in `architect.md`); it keeps `Bash` so it can run tests and `git diff`, which means read-only is a convention, not an enforced boundary.

These are configurable defaults, not equivalence, quality, cost or availability guarantees. Confirm effort settings and availability in each supported client during implementation. Existing standard agents and their defaults must not silently change on upgrade; this includes the current utility, architect and grader behavior. Record any validated default change in the README and upgrade notes. An unavailable configured model must produce a clear warning or client error; do not silently claim a small model was used.

For Cursor, verify current model-selection support before committing to a mapping. If supported reliably, use an explicit model. Otherwise preserve `inherit`, state clearly that the small role controls instructions rather than guaranteeing model size, and let the developer select the actual model. For Codex, add explicit client-specific model mapping rather than passing Claude aliases through the existing converter; never assume Claude model aliases exist in Codex. Shape: one table in `vendors.py`, `CLIENT_MODELS[(tool, role)] -> (model, effort) | None`, where `None` keeps today's behavior (Cursor `inherit`, Codex no model); `convert_agent` reads it instead of the hardcoded `inherit`, and standard roles map to `None` so their output cannot change. Override UX for v1: edit the generated agent file (re-runs skip it without `--force`, which already protects the edit). No flags or config file. Reasoning effort and model are independent settings and must use values supported by that client/model.

## Delegation and review

1. **Choose the role.** Use small coders for clear, bounded work with concrete acceptance criteria and verifiable outcomes. Larger tasks may be split into independent blocks; length alone is not a reason to use or reject the small tier. Use the standard coder or architect for unresolved behavioral decisions, broad interaction risks, unclear specifications or repeated failures. Honor a developer's explicit model or role choice.
2. **Brief the coder.** Give the goal, relevant paths, allowed scope, behavior and edge cases, acceptance criteria, verification commands, dependencies, integration base and how to report blockers. Preserve the shared language-specific tool instructions and forbid unrelated edits, unapproved dependencies, memory writes and git operations unless the brief authorizes them. Small coders stop and report consequential ambiguities rather than inventing design decisions.
3. **Review independently.** The orchestrator gives `code-reviewer` the original brief, relevant specification, exact diff or isolated worktree and base, test results, and known uncertainties. Ask for correctness, regressions, missing requirements and meaningful verification; do not suggest a verdict. The reviewer is read-only, provides prioritized findings with file/line evidence, and distinguishes verified behavior from assumptions. A review is not a substitute for required tests or the SDD final grade.
4. **Repair and re-review.** Send findings to the same coder when practical. Re-review the resulting diff, especially changes addressing material findings. The orchestrator owns unresolved findings, integration and the final report; after repeated failure or unresolved design questions, escalate to the standard coder or architect. Never silently accept failed review. If an independent reviewer cannot be launched, tell the developer and follow project instructions rather than claiming independent review took place.
5. **Parallelize safely.** Assign independent blocks with clear ownership and dependencies. Use isolated worktrees when supported and appropriate; coordinate overlapping changes and review/integrate each result against its actual base. Avoid destructive worktree operations and follow the existing worktree workflow and user instructions. No blanket requirement to create worktrees for every task. Run relevant checks after integration; report skipped checks and conflicts. A coder does not commit or merge unless its brief authorizes it.

Review applies to small-coder implementation, including fixes to findings. For trivial read-only utility results, the orchestrator can verify them directly; don't spawn a reviewer for every command. Existing SDD approval gates, the architect and grader contracts, and memory ownership remain intact.

## Installation and upgrade design

Small variants and the reviewer are part of the coder install, not a separate feature. There is no new flag and no new option.

Install rules:

- Whenever a normal coder agent is installed, its small variant is installed with it: generic `coder` -> `coder-small`; each language coder (full install or standalone `coders` command) -> `coder-<lang>-small`. Languages are never added beyond what was selected; MCP servers stay shared, not duplicated.
- `code-reviewer` is installed whenever any coder agent (generic or language) is installed, independent of SDD. It has no component name of its own: it is tied to coders, and `--without` excludes it only by excluding all coder agents. Rationale: a separate exclusion adds a combination to test for little value, and small output without a reviewer would break the review loop.
- Consequences for `--without`: `--without agents` omits the generic `coder`/`coder-small` but language specialists, their small variants and the reviewer still install; `--without sdd` and `--without agemem` change nothing about these agents. If no coder agent is installed, neither are small variants nor reviewer.
- Re-runs and dropped components: the small agents behave exactly like the normal coder agents. A re-run adds missing files, leaves differing (customized) files untouched without `--force`, reports `unchanged` otherwise; omitting a component with `--without` does not delete anything already installed. No special-casing, no deletion.

Concrete shape (names are proposals; keep them unless the spike contradicts them):

- No `Options`/`cli.py` change.
- `assets/agents/tiers/code-reviewer.md` and `assets/agents/tiers/coder-small.supplement.md` (short text appended to the shared coder body; the generic `coder-small` is `coder.md` with `name/description/model: haiku/effort: high` overridden plus the supplement).
- `coders.py`: `small_agent(coder) -> f"{coder.agent}-small"`; `agent_bytes(coder, memory, small=False)`; `Coder.section_text()` always names both tiers (the standard text is rewritten in place, since it is a marker section); `status()` reports small variants (extra `small` column in `list_coders`).
- `agents.py`: `install_tier_agents(ctx, tools, memory, generic, reviewer)` called from `_run_install` and `_run_coders` right where the standard coders are installed, so presence is decided by the same selection logic. Because small agents are always present with coders, routing needs no "small tier present" detection: wherever the standard coder is named, the small counterpart is named too.
- Tier guidance goes in a new `.agents/delegation-tiers.md` written via `write_bytes` whenever coders are installed, referenced from the routing section. It names only roles installed with coders (small coders, reviewer), never `architect`, `code-grader`, `utility` or SDD. Do not edit `development-workflow.md` for this (see code facts); a one-line pointer in the workflow is acceptable only if the tests are updated deliberately and the change is called out in CHANGELOG.
- Parameterize generation by role/tier: reuse the current coder body and the exact same language fragment and navigation tool list, with the concise small-coder supplement. Avoid copying long prompts or diverging language tool lists. Distinct names and descriptions must make the two roles discoverable.
- Update the generated language routing section so language choice and model tier are separate: Python changes always go to a Python specialist, standard or small according to the workflow and developer choice. Multi-language work may be split by language. Instructions never refer to agents that were not installed (a user who deleted a small file gets it back on the next re-run).
- Extend role metadata and client conversion deliberately. Preserve model and reasoning fields when copying or converting between clients where appropriate; don't accidentally translate a custom source agent into a different model. Preserve client-specific read-only restrictions where supported and use explicit instructions otherwise; document that instructions alone are not an enforcement boundary.
- Re-runs, dry runs, `--force`, collision handling, status/list output and personal mode must account for each new agent and the reviewer. Preflight reports the precise files and any conflicts before writing. Existing customized agents, navigation servers, unrelated settings and unmarked instructions remain protected. Print clear upgrade messages (new agents added by this version) and unavailable-model messages.

## Execution protocol (multi-agent)

Evidence from a comparable QA-then-fix campaign: cheap fixers (Haiku, high effort, one worktree each, 3 in parallel, one commit plus a `git format-patch` per block) worked, but a Sonnet reviewer found real defects in about one block in three (silent wrong writes, over-broad refusals, missing end-to-end tests, wrong trailer). Typical fixer failures: skipping black-box replays, unit-only tests, edits outside scope, overwriting shared scratch dirs, stopping on rate limits. Apply this:

1. **Blocks.** One block per work package above (WP2 may split into vendors/coders vs agents/assets if the interface in "Concrete shape" is fixed first). Max 3 in parallel and only blocks with disjoint file lists. The lead (Opus/Sonnet) owns WP0, WP1 review, WP6, integration and final checks; Haiku is acceptable for WP3/WP5 text and docs, Sonnet for WP2/WP4 code.
2. **Isolation.** Each fixer gets its own worktree from the current integration commit and its own scratch dir `/tmp/<wp>-<agent>/` (never a shared path). Brief states the base commit, the allowed file list (anything else changed is rejected), the acceptance bullets it owns and the black-box replay above.
3. **Deliverable per block.** One commit plus `git format-patch -1` output, a report listing files changed vs the allowed list, test commands with results, replay output, and the exact commit trailer: `Co-Authored-By: <the model name the session is actually running>` per the session's attribution reminder (check it; do not copy another agent's). The reviewer verifies the trailer.
4. **Review.** A reviewer per patch (Sonnet, read-only) gets the brief, the patch and the acceptance bullets, and must end with `VERDICT: APPROVE` or `VERDICT: CHANGES` plus numbered findings. A reply with no verdict counts as not reviewed: re-run it. It checks specifically: silent wrong writes (what happens on `skipped`/conflict), over-broad refusals, an integration-path test for each acceptance bullet, standard-agent bytes and the golden test changed only where the WP allows (WP4), files within scope, trailer. The fixer amends once; the reviewer re-checks only the amended hunks; a second failure goes to the lead.
5. **Integration.** The lead cherry-picks approved commits in dependency order, resolves conflicts, then runs `uv run pytest -q`, the golden and upgrade tests, `uv build` and the replay on the merged tree. Never merge a block whose review lacks a verdict.
6. **Resilience.** A fixer that stops on a rate limit leaves its worktree intact; the lead resumes it with the same brief (SendMessage) or restarts it from its last commit. Never delete a worktree with unreviewed work; use `trash` for cleanup of scratch dirs only.
7. **Rollback.** Changes are additive (new files; marker sections rewritten in place); to back out, revert the integration commits (one per block). Generated files in a user's project are not removed by a re-run; document `trash .claude/agents/*-small.md ...` style cleanup in the README rather than automating deletion.
